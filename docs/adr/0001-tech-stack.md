# ADR 0001：技术栈与总体架构

- 状态：已采纳
- 日期：2026-11-17

## 背景

Isle Settlers 是一款六边形岛屿上"开拓、交易、建造"的回合制桌游 Web 版，目标：

1. 完整实现该类桌游基础版的全部规则（之后扩展到 5–6 人和扩展包）；
2. 联机对战，第一版通过**邀请链接**开房间，不做账号；
3. 有 AI 对手，难度分层；
4. 前后端同一个仓库；
5. 追求极限性能；
6. 类 3D 画风。

名称、美术和视觉设计全部原创，不使用任何现有商业桌游的商标、美术或卡牌设计。

## 关键判断：性能瓶颈在 AI，不在网络

回合制游戏一局平均每秒不到 1 条消息，单机即可承载上万房间，网络框架的吞吐量差异对我们没有实际影响。性能预算花在：

| 热点 | 原因 |
|---|---|
| 规则引擎 | AI 搜索（Expectimax / ISMCTS）每步要模拟大量局面，引擎速度直接决定 AI 强度 |
| 客户端响应 | 浏览器内用同一份规则代码做本地校验，点击后 16ms 内反馈，不等服务器往返 |
| 首屏加载 | 邀请链接点开就要能玩 |

## 决策

| 层 | 选型 | 理由 |
|---|---|---|
| 规则引擎 | **Rust**（`isle-core`），零依赖、无堆分配、`Copy` 状态 | 同一份代码编译成原生（服务器权威判定、AI）和 WASM（浏览器），规则只写一遍 |
| AI | **Rust**（`isle-ai`） | 原生速度；离线人机模式可以在浏览器 Web Worker 里跑 WASM |
| 服务器 | **axum + tokio**，每个房间一个 Actor（tokio task） | 原生、无 GC；最终打成一个静态二进制并内嵌前端资源 |
| 传输 | **WebSocket**，协议层做抽象 | WebTransport 已在 2026 年 3 月成为 Baseline，但它的优势（不可靠数据报、无队头阻塞）对回合制没有意义，反而多出 QUIC/UDP 的部署成本 |
| 序列化 | **JSON 文本帧**（serde_json ↔ 浏览器原生 `JSON.parse`），TS 类型由 Rust 生成。P2 修订：原计划用 bitcode | 浏览器端零解码代码、便于调试；单条视图约 2–3 KB，回合制下带宽不是瓶颈。以后若需要，可在协议层换成二进制 |
| 类型共享 | ts-rs / tsify 从 Rust 生成 TS 类型 | 协议一改，前端编译期就报错 |
| UI | **SolidJS + Vite** | 细粒度响应式、无虚拟 DOM、运行时极小 |
| 3D 渲染 | **Three.js**，`WebGPURenderer`（自动回退 WebGL2），锁定版本 | 体积小于 Babylon.js，生态最大，满足类 3D 画风 |
| 资源管线 | Blender → glb → gltf-transform（meshopt / KTX2） | meshopt 解码比 Draco 快 |
| 存储 | 对局事件溯源：种子 + 动作序列。P2 先用每房间一个 JSON 文件（原子写），之后需要查询或统计时再迁 SQLite / Postgres | 断线重连、观战、回放、AI 训练数据，全部来自同一份日志；重启时重放即可恢复 |
| 仓库 | Cargo workspace + pnpm workspace | 一个仓库，一条命令构建 |

## 规则引擎设计

- **拓扑在编译期生成**：`build.rs` 生成邻接常量表：基础岛屿 19 个地块、54 个交叉点、72 条边；P4 起还有 30 块的扩展岛屿（80 个交叉点、109 条边）。顶点集合和边集合都用 `u128` 位板（P3 之前顶点用 `u64`），坐标用精确的整数格点（不用浮点去重）。
- **状态是定长 `Copy` 结构体**，没有堆分配，复制一次就是一次 `memcpy`，适合 MCTS 频繁克隆。
- **确定性**：随机数（xoshiro256++）存放在状态里，`(config, seed, actions)` 可以完整复现一局，原生和 WASM 结果一致。服务器持有种子，客户端和 AI 看不到。
- **`check` / `execute` 分离**：校验失败时状态不变；`apply_with` 通过 `EventSink` 输出事件，传 `()` 时零开销（供 AI 搜索使用）。
- **合法走法**写入可复用的 `Vec`，热路径上不分配内存。开放式的玩家间交易报价不枚举，bot 自行生成后用 `check` 校验。
- **测试**：每条规则都有场景测试。随机自对弈模糊测试每一步都会检查资源守恒、发展卡守恒、棋子数量、距离规则和最长道路缓存，并交叉验证 `legal_actions` 与 `check` 判断完全一致，以及非法动作不会修改状态。
- 规则细节和取舍见 [`docs/rules.md`](../rules.md)。

## 隐藏信息与 JS 边界（P1 补充）

- **按玩家投影**：服务器（以及浏览器内的对局托管）从不发送原始 `GameState`，只发送 `isle_proto::player_view(state, viewer)` 投影出的 `PlayerView`，以及经过 `Event::redacted_for(viewer)` 隐去私密信息的事件。隐藏信息包括：对手手牌构成、对手发展卡、牌堆顺序、随机数状态；牌的**数量**是公开的。测试会打乱所有隐藏信息，然后断言每个座位看到的视图完全不变。
- **浏览器内对局**：`MatchHost`（纯 Rust，可原生测试）托管人类座位加 bot 座位；JS 只拿得到人类座位的视图。P2 联机时，服务器使用同样的投影。
- **JS 边界用 JSON 文本**：`serde_json` 序列化，浏览器端用原生 `JSON.parse` 解析。
- **人类操作按序号提交**：UI 从带版本号的 `legalActions()` 列表里选一个序号，WASM 端不需要反序列化 Action。实测仅 Action 反序列化一项就会让 WASM 增加约 38 KB（gzip）；交易报价不在列表里，单独走 `proposeTrade(give, get)`。版本号用于拒绝过期的序号。
- **TS 类型由 Rust 生成**（ts-rs）：`web/src/generated/proto.ts`。枚举采用 `{ type, value }` 判别联合，前端可以做穷尽匹配；生成文件与 Rust 不同步时测试会失败。

## 联机（P2 补充）

- **连接与协议**：只有一个 WebSocket 端点 `/api/ws`。第一条消息是 `Create` 或 `Join`，服务端回 `Joined { room, seat, token }`。之后服务端推送四类消息：`Room`（座位和在线状态）、`Snapshot`（开局或重连时的完整状态和最近日志）、`Update`（每个动作之后的视图、合法动作和事件）、`Chat`。所有视图和事件都按接收者的座位投影。
- **房间 Actor**：每个房间一个 tokio 任务，独占权威 `GameState`，逐条处理消息，不需要锁。同一视角的更新只序列化一次，再发给该座位的所有连接。
- **邀请链接与身份**：房间码 8 位，用无歧义字母表生成。每个座位一个 128 位随机 token，存在浏览器 localStorage 里，用于重连。第一版没有账号（P4 加了可选账号，见下文"账号接口与登录"）；未知 token 会被当作新加入者处理，开局后加入的人成为观众。开局前房主断线时，房主身份移交给第一位在线的真人玩家。
- **出牌校验**：客户端直接发送 Action（取自服务端下发的合法动作列表），服务端一律用规则引擎对当前状态校验，版本号只作参考。客户端同一时间只允许一个动作在途，防止连点。
- **bot 与托管**：空位开局时由 bot 补上；玩家掉线超过 30 秒（可配置），由 GreedyBot 代打（"托管"），重连后立即交还控制权。**所有真人都离线时整局暂停**，不会出现回来发现对局已经被 AI 打完的情况。bot 出手有可配置的延迟，方便真人跟上节奏。
- **健壮性**：每 20 秒发一次心跳，50 秒内收不到任何数据就断开；每个连接的发送队列有上限（512 帧），慢客户端会被断开，重连后靠快照恢复；单条消息最大 16 KB；聊天限速并清洗内容；空闲房间超时回收（大厅 15 分钟、对局 60 分钟、结束后 10 分钟）。
- **持久化**：房间存档包含种子、座位和完整动作日志，变化后 250 ms 内合并写盘（临时文件 + rename）。启动时重放恢复，关停（SIGTERM / Ctrl-C）时先存盘再退出。集成测试覆盖了"重启前后视图和合法动作完全一致"。
- **部署**：单个二进制同时提供前端静态资源（带哈希的资源设置 immutable 缓存并启用 gzip）和游戏协议；提供 Dockerfile（多阶段构建，运行时镜像以非 root 用户运行，`/data` 挂成卷）。
- **已知限制**：单机进程内存放所有房间，没有做水平扩展（以后可以按房间 ID 做粘性路由）；有人在线但长时间不操作时不会自动托管（还没有回合计时器）；手机上没有显示聊天面板；不支持踢人和重新排座。

## 渲染设计

- **按需渲染**：只有相机移动或状态变化时才绘制，回合制大部分时间画面静止，此时 GPU 占用为零。
- **InstancedMesh**：地块、装饰、道路、村庄、城市和可落子标记各一个批次，整个场景（含阴影 pass）约 95 次绘制调用。
- **点击拾取不做网格射线检测**：指针射线与桌面平面求交，再吸附到最近的高亮位置；拖拽和点击按位移与时长区分。
- **避让 HUD**：App 测量带 `data-inset` 标记的面板，渲染器用 `setViewOffset` 把岛屿放进剩余的空白区域，并保留玩家当前的视角和缩放。
- **动画**：新棋子落下、强盗移动、骰子、资源从地块飞到对应玩家，均在动画期间才持续渲染。
- **WebGPU 设备丢失时自动重建为 WebGL2**；也可以用 `?renderer=webgl` 强制使用 WebGL2。
- Three.js 单独一个 chunk，懒加载：HUD 先渲染，3D 场景随后加载。
- 原创 low-poly 风格，模型用代码生成（尚无贴图），后续换成 Blender 模型。

## 实测数据（v0.1，本仓库首个提交）

测试环境为 4 vCPU 云容器，bot 是加权随机，4 人局。

| 指标 | 数值 |
|---|---|
| 原生单线程 | 约 12,600 局/秒（每局约 650 个动作，约 820 万动作/秒） |
| 原生 4 线程 | 约 37,700 局/秒（约 2,470 万动作/秒） |
| 开启每步不变量检查 | 5,000 局全部通过 |
| 浏览器 WASM（无头 Chromium 主线程） | 约 6,500–8,100 局/秒 |
| `isle_wasm_bg.wasm`（v0.1：引擎 + bot） | 59.7 KB，gzip 后 26.8 KB |
| `isle_wasm_bg.wasm`（P1：+ 视图投影、JSON、GreedyBot、对局托管） | 107.8 KB，gzip 后 46.5 KB |
| 首屏 JS（v0.1 / P1 完整对局界面） | gzip 后 9.8 KB / 20.6 KB |
| Three.js chunk（懒加载） | gzip 后 240 KB |

> Three.js 的 WebGPU 构建比纯 WebGL 构建大 70 KB 左右（gzip）。如果以后首屏体积比 WebGPU 收益更重要，可以换回 `WebGLRenderer`，只需改一处。

## AI 路线

| 难度 | 实现 | 状态 |
|---|---|---|
| 简单 | 加权随机（`WeightedRandomBot`） | ✅ |
| 普通 | `GreedyBot`：目标驱动的启发式。开局按点数、稀缺度、多样性和港口选点；围绕目标建筑做海上贸易；强盗打领先者；弃牌保目标。只用公开信息和自己的手牌 | ✅ 对 3 个简单 AI 胜率 99.5%（4000 局） |
| 困难 | `MctsBot`：信息集蒙特卡洛树搜索（ISMCTS），见下文 | ✅ 对 3 个普通 AI 胜率约 48%（基线 25%） |
| 专家（可选） | 自对弈训练价值/策略网络，替换手写评估函数 | 未做 |

## AI（P3 补充）

- **确定化（`isle_ai::determinize`）**：搜索前，把 bot 看不到的信息全部重新随机生成，包括对手手牌、对手发展卡、牌堆顺序和随机数（未来的骰子和抢牌结果）。对手手牌合起来的构成是公开可推的（总数减去银行和自己手里的），未知的只是每人各拿了哪几张，所以只随机这部分。发展卡同理：从未出现过的牌里，按公开的持牌数分给各对手，剩下的就是牌堆。确定化的结果只取决于公开信息、自己的手牌和随机种子。有测试打乱真实的隐藏信息后，断言确定化结果和最终决策都完全不变，所以 AI 从结构上就不可能作弊。
- **搜索（`isle_ai::MctsBot`）**：单观察者、开环的 ISMCTS。
  - 每次迭代都重新确定化，同时处理隐藏信息和骰子随机性。
  - 所有确定化共用一棵按动作序列索引的树；选择时用 UCB1，并按动作的"可用次数"修正，因为不同确定化下合法动作不同。
  - 多人博弈按 max^n 处理：每个节点记录"做出该动作的座位"的收益。
  - 展开时，开局选点、弃牌、移动强盗这几类分支很宽的动作，先按启发式只保留最好的 8 个。
  - 离开树后，用快速策略模拟 8 个回合，再由评估函数估算各座位的胜率并回传。
  - 交易回应（接受/拒绝）也是搜索出来的。
- **评估函数（`isle_ai::eval`）**：以分数为单位估算局面强弱，包括分数、按稀缺度加权的期望产出、资源种类、能立即建村庄的空位、手牌（超过 7 张扣分）、未打出的发展卡、骑士和最长道路的进度、港口与自身产出的匹配度。各座位的得分经 softmax 转成胜率估计；终局时赢家为 1，其余为 0。
- **调参**：用 `isle-sim --rotate` 轮换座位做锦标赛，消除先手偏差，结果附 95% 置信区间。MCTS 坐一个座位，另外三个是 GreedyBot；双方实力相当时的基线胜率是 25%。

  | 配置（迭代次数 / 模拟回合数） | 胜率 | 局数 |
  |---|---|---|
  | 1000 / 8 | 38.3% ± 5.5 | 300 |
  | 1000 / 8，探索常数 0.25 或 1.0 | 38.3% / 37.7% | 各 300 |
  | 1000 / 4、1000 / 16 | 36.7% / 38.0% | 各 300 |
  | 1000 / 8，产出权重 4.0 或 1.2 | 31.7% / 39.7% | 各 300 |
  | 1000 / 0（不模拟，直接评估） | 47.3% ± 5.6 | 300 |
  | 1500–4000 / 0 | 40.3%–44.0% | 300–600 |
  | 1500 / 0，加"建造潜力"项（权重 0.5 / 1.0） | 41.5% / 33.3% | 各 600 |
  | **4000 / 8（默认）** | **48.0% ± 5.7** | 300 |

  对付 GreedyBot 时，不模拟的便宜配置看起来和默认配置差不多，但两者直接对局（再加两个 GreedyBot，400 局）时，默认配置胜率 **40.5% ± 4.8**，便宜配置只有 28.5% ± 4.4。所以默认采用 4000 次迭代、模拟 8 个回合。
- **耗时**（每个需要搜索的决策，`cargo run --release -p isle-ai --example think_time`）：原生平均 32 ms，最长 78 ms；浏览器 WASM 里平均 38 ms，最长 96 ms。服务端的 bot 一律在 `spawn_blocking` 线程池里思考，不阻塞异步运行时；浏览器端整个本地对局跑在 Web Worker 里，AI 思考时界面不卡顿。
- **WASM 改用 `opt-level = 3`**：按体积优化的 `"z"` 会让搜索慢约 4 倍（平均 145 ms，长尾超过 1 秒），而改成 3 后 gzip 体积只多 6 KB。现在是 186 KB，gzip 后 76 KB（P1 是 46 KB）。
- **尚未做**：AI 主动向其他玩家发起交易（目前只回应）、跨步复用搜索树、利用对手出牌历史推断手牌（现在是在公开约束下均匀采样）、用自对弈学习替换手写评估函数。

## 5–6 人扩展与回放（P4 补充）

- **运行时选择拓扑**：`build.rs` 为每种岛屿生成一张静态 `Topology` 表（`BASE`、`EXTENDED`），`GameState::topo()` 按棋盘的 `BoardLayout` 取用。状态里的数组按最大尺寸分配（6 个座位、30 个地块、11 个港口、34 张发展卡），多出来的位置只是填充，状态仍然是无堆分配的 `Copy` 结构体。人数决定岛屿：5–6 人用扩展岛屿，其余用基础岛屿。
- **基础局完全不变**：重构必须保证已存档的房间和回放照常重放，所以基础岛屿的编号、随机数消耗顺序都与之前逐字节一致。`cargo run --release -p isle-ai --example fingerprint` 对 300 局加权随机、60 局 GreedyBot、6 局 MCTS 的全部动作取哈希，重构前后结果相同；自对弈统计（平均动作数、各座位胜率）也一致。位板改成 `u128` 后原生速度没有下降（单线程约 520 万动作/秒）。
- **特殊建造阶段**：新增 `Phase::SpecialBuild { builder }`。轮到谁特殊建造，`to_move()` 就返回谁，所以服务器的 bot 调度、托管和浏览器端的对局托管都不用改。合法动作只有建造、买卡和跳过；胜利判定在这个阶段暂停，回合真正交给下家时再判定。新增事件 `SpecialBuildPassed`。
- **AI**：GreedyBot 和 MCTS 的快速模拟策略在特殊建造阶段直接复用主阶段的建造逻辑（合法动作列表本身已经排除了交易和打卡）。6 人局 MCTS 每次决策原生平均约 107 ms（4 人局约 49 ms），只用 1000 次迭代时，对 5 个 GreedyBot 胜率 35.0% ± 8.5（基线 16.7%，120 局）。
- **前端**：渲染器按棋盘的拓扑重建格点、沙滩和相机取景。沙滩是地块中心凸包向外偏移得到的多边形台面，港口朝向所在地块的外侧，相机按岛屿的实际宽高取景。新增紫色、青色两种玩家颜色。特殊建造时只显示建造按钮和"跳过"，本地对局里 bot 跳过时的节奏也比正常出手快。
- **回放**：
  - 格式 `ReplayRecord`：配置、种子（十进制字符串，因为 `u64` 超出 JS 数字精度）、玩家名单（真人名字或 AI 难度）、紧凑编码的动作日志、赢家。每个动作编码为"座位字节 + 标签字节 + 操作数"，平均 3–4 字节，比 JSON 形式的动作小 5–10 倍。
  - 服务器在终局时把回放存进内存缓存（最近 256 局），有数据目录时同时写入 `<数据目录>/replays/<id>.json`；`GET /api/replays/{id}` 返回 JSON，里面没有座位 token。房间信息 `RoomInfo.replay` 带上回放 id，前端据此生成分享链接 `#/replay/ID`。
  - 浏览器端的本地对局由 `MatchHost` 记录动作日志，终局时 Worker 随状态一起返回回放。
  - 播放器 `isle_wasm::Replay`：加载时完整重放一遍做校验，每 32 步存一个检查点，跳转时从最近的检查点重放，所以拖动进度条是即时的。可以切换到任意座位的视角查看手牌，事件按该视角隐去私密信息。前端的 `ReplaySource` 实现了和本地、联机对局相同的 `GameSource` 接口，界面代码全部复用。
  - **JS 边界保持只出不进**：回放 JSON 由浏览器原生解析，再把各字段和动作字节数组交给 WASM。最初的实现在 WASM 里用 serde 反序列化整份记录，体积从 186 KB 涨到 378 KB（gzip 后从 76 KB 涨到 143 KB），其中 Action 的派生反序列化一项就占 34 KB；改成字节编码后是 213 KB，gzip 后 88 KB。
- **本机回放列表**：浏览器保存最近 20 场已结束的本机对局，可在大厅按人数、赢家、地图种子或日期搜索。不自动保存或公开联机回放；浏览器禁用存储时自动降级。
- **嵌入单人版与跨平台构建**：`pnpm build:embed` 生成面向无后端静态托管或沙箱网页的单机版本（相对路径资源、隐藏联机与下载入口、固定使用 WebGL2）。WASM 与嵌入版构建脚本均采用 Node 编写（`scripts/build-wasm.mjs`、`web/scripts/build-embed.mjs`），在 Windows、Linux 与 macOS 下一致可用。
- **账号与会话存储**：`isle-server` 提供用户名规范化与 Argon2id 密码哈希（`accounts`），以及基于 SQLite（WAL、`synchronous=FULL`）的账号与 SHA-256 会话持久化存储（`account_store`，含防时序侧信道登录校验与过期会话清理）。
- **账号接口与登录**（`auth.rs`）：
  - 登录方式是用户名 + 密码，账号可选，游客照常玩。账号放在 `--data-dir` 里，没有数据目录就不开账号（`/api/health` 的 `accounts` 告诉前端是否显示登录）。账号库损坏或不是本程序的库时服务器拒绝启动，而不是悄悄关掉账号。
  - **会话用 Bearer token，不用 Cookie**：前端把 token 存在 localStorage，HTTP 请求放在 `Authorization` 头里，联机时随 `Create` / `Join` 发送。这样没有 CSRF 和跨站 WebSocket 劫持的问题，也和已有的座位 token 一致；代价是页面出现 XSS 时 token 可能被读走，所以服务端只存 token 的 SHA-256，会话可以单个或全部撤销，并默认 30 天过期。界面全部用 Solid 的文本绑定渲染，没有把用户输入当 HTML 插入。
  - **Argon2 的代价控制**：哈希放在阻塞线程池上，最多同时占一半核心（默认参数每次约 19 MiB 内存），排队超过 10 秒返回 `Busy`。注册和登录共用一个按客户端地址的令牌桶（10 次突发，之后每 6 秒 1 次，IPv6 按 /64），超出返回 429 和 `Retry-After`。放在反向代理后时用 `--client-ip-header` 指定可信的地址头。查会话（SHA-256 + 主键查询）不限流：token 有 256 位，猜不中。
  - **座位绑定账号**：带有效会话加入时，座位记下账号 id 和用户名（随房间存档），名字固定为用户名并在界面上标 ✓。同一账号在任何设备上加入都会拿回这个座位，所以换设备、清空浏览器也不丢座位；座位 token 仍然优先，退出登录不影响已经坐下的对局。前端只在没有该房间座位 token 时才发送会话，避免断线重连因为会话在别处被注销而失败。无效会话返回 `SessionExpired`，前端清掉本地登录并提示重新登录。
  - 用户名只能是 ASCII（`a-z0-9_-`），所以暂时不能用中文名；以后如需中文昵称，可以给账号加一个单独的显示名。
- **排位**（`rating.rs`、`ranking.rs`）：
  - **评分算法选 Weng-Lin（Plackett-Luce 模型）**。Elo 和 Glicko 本是两人对局的算法，多人局只能拆成两两比较，和名次的关系是硬凑的；TrueSkill 效果好但有专利和商标。Weng-Lin（JMLR 2011，OpenSkill 采用）直接按一局的完整名次更新，支持并列，每人带均值 μ 和不确定度 σ，更新是闭式公式，几十行就能实现。参数用论文和 OpenSkill 的默认值：μ₀=25、σ₀=25/3、β=σ₀/2、κ=10⁻⁴，每局前 σ 增加 τ=μ₀/300，让分数能跟上进步。单元测试用 OpenSkill 公开的数值核对。
  - **显示保守分** `1000 + 25(μ − 3σ)`，而不是 μ。新人从 1000 起步，随着 σ 变小逐步爬升；运气好连赢两局的新人 σ 还大，不会排到老玩家前面。前 5 局为定级赛（可用 `--placement-games` 调整），期间不给段位、不上榜。分数刻度和段位线（青铜到大师，每 150 分一档）是用 60 名不同实力的模拟玩家各打约 400 局校准的：长期中位数约 1500（铂金），最强约 1850，排序和真实实力一致。
  - **哪些对局计分**：房间分「排位 / 休闲」，开局前房主可切换。排位房间里至少两名登录玩家才计分；AI 和游客参与对局但不计入名次比较。名次是赢家第一，其余按终局分数，同分并列；掉线托管的玩家照常计分（中途离开要承担结果）。
  - **只算一次**：终局时房间 actor 在阻塞线程池里写库，以回放 id 为主键记录对局；重复记录（重试、崩溃后重启、恢复房间）直接返回第一次的结果，所以评分不会重复计算，重启后结算界面也能重新显示分数变化。写库失败时 30 秒后重试。
  - **数据**放在账号库里（schema v2：`ratings`、`matches`、`match_players`），v1 的库在打开时原地迁移。排行榜和玩家主页是公开接口，不需要登录。
- **尚未做**：其他扩展包、联机回放列表与搜索、观战时的回放式时间轴。

## 航海扩展（P4 补充）

- **原创地图，复刻机制**：船、移船、海盗、金矿、发现新岛奖励这些机制来自航海类扩展；地图「群岛」、名称和美术都是原创，没有照搬任何官方剧本的布局。
- **地图受掩码宽度约束**：交叉点和边都用 `u128` 位掩码，所以一张地图最多 128 个交叉点、128 条边。海也要算格子（船要在海格的边上走），所以能用的格子大约 35 个。最初设计的 32 格、三个小岛的版本，用脚本量出主岛和每个小岛之间只有 1 条边：尖顶六边形错行时隔一格海，顶点仍然只差一条边，一艘船就能登岛，探索没有意义。最终版是 33 格（90 个交叉点、122 条边）：主岛与小岛之间隔两格海，至少 3 条边；两个小岛之间留一条窄海峡。`build.rs` 用文字地图生成拓扑，并在编译期检查岛屿连通、不共用交叉点、港口朝海、海盗起点唯一。不改掩码宽度，引擎和 AI 的热路径完全不受影响。
- **海与陆按格子推导**：`Board` 从地形推出陆地边、临海边、陆地交叉点、岛屿编号和开局区域，规则判断都是一次位运算。经典地图上陆地边等于全部边、开局区域等于全部交叉点，原有判断的结果不变。
- **一个动作两种用途**：`MoveRobber` 点陆地移强盗、点海面移海盗，不新增动作。金矿是新阶段 `Phase::Gold`：和弃牌一样，所有该选的人按任意顺序各提交一次 `ChooseGold`，开局时选完再放道路或船。新动作 `BuildShip`、`MoveShip`、`ChooseGold` 的回放编码是 17–19，旧回放和存档照常读取（`GameConfig.scenario` 缺省为经典）。
- **最长商路**：搜索时记住上一段是路还是船，只在自己的建筑处允许换乘；经典局里没有船，结果和原来逐位相同。模糊测试据此发现了一个漏洞并已修复：在自己路和船的交汇处建村庄会把两段接起来，原来的代码不会重算建造者自己的长度。
- **经典局不受影响**：所有航海逻辑都按地图开关，合法动作列表的内容和顺序在经典局里不变，确定性指纹仍是 `b862d3b3842bae2d`。
- **AI**：共用一个海路搜索（`isle-ai/src/sea.rs`），从自己的建筑和船队末端出发，沿空闲、不挨海盗的临海边做广度搜索，找村庄空位；新岛上的空位加上奖励价值，按还需要的船数打折。
  - 贪心 AI 用它给造船和移船打分；陆地没有更好的扩张时转为造船；能登岛、且手牌离造船更近时，造船优先于升城市。这条调整把人均登岛次数从 0.28 提到 0.49，对局也略短。
  - MCTS 的评估函数加入金矿产出和"离新岛还有多远"一项，推演策略会造船、按需要选金矿。
  - 默认 MCTS 对三个贪心 AI 的胜率是 38%（随机基线 25%）；每步本机约 124 ms，经典地图是 65 ms。
- **渲染**：
  - 海格不画成凸起的地块，只画浅水纹标出航行网格；每个岛单独一圈海滩。小岛的凸包是尖三角，所以扩边时锐角改成平角，避免两个小岛的沙滩在海峡处连起来。
  - 船停在临海边上并向海一侧偏移，海盗是一艘黑帆大船。港口方向改为"从陆地格指向海"，而不是"指向唯一相邻的格"。
  - 海岸边既能修路也能造船时，弹窗让玩家选择。
- **WASM 体积**：213 KB → 259 KB（gzip 88 KB → 106 KB），多出来的是航海规则和 AI 的海路搜索。

## 考虑过但没选的方案

| 方案 | 不选的原因 |
|---|---|
| 全 TypeScript（Bun + uWS） | 开发快，但 AI 搜索性能明显吃亏 |
| boardgame.io / Colyseus | 前者维护不活跃；后者绑定 Node 和它的状态同步模型 |
| Bevy / Leptos 全栈 Rust | WASM 体积好几 MB，首屏慢；用 Rust 写 UI 效率不如 Solid |
| Babylon.js | 全量引入约 1.4 MB，物理和 GUI 我们用不上 |
| PixiJS（2D） | 不满足类 3D 画风 |

## 路线图

1. **P0（已完成）**：规则引擎、基线 bot、自对弈基准、WASM 绑定、3D 棋盘骨架。
2. **P1（已完成）**：浏览器内人机对局：大厅、点击建造、交易（银行与玩家）、发展卡、弃牌与强盗、动画、观战模式；按玩家投影的视图；GreedyBot；嵌入单人版构建；端到端测试。

4. **P3（已完成）**：困难 AI：确定化 + ISMCTS + 评估函数，锦标赛调参；服务端阻塞线程池、浏览器 Web Worker。
5. **P4（进行中）**：✅ 5–6 人扩展（扩展岛屿、特殊建造阶段）；✅ 回放（服务器存档与分享链接、本地下载与载入、本机回放列表与搜索、进度条与视角切换）；✅ 账号（SQLite + Argon2id 存储、注册登录接口、前端登录、座位绑定账号、登录限流）；✅ 排位（Weng-Lin 评分、段位与定级赛、排行榜、玩家主页与对局记录）；✅ 航海扩展（原创群岛地图、船与移船、海盗、金矿、登岛奖励、会出海的 AI）；待做：其他扩展包。
